## Решение

Перевести учебную платформу на вариант 02 из [design-directions.html](design-directions.html): графитовая боковая навигация, светлая рабочая область, компактные строки, вкладки и заметное основное действие. Выбранный вариант становится основой всех экранов обеих ролей. Предыдущая рекомендация смешивать направления 01/04/02/03 из design-directions.md для этой задачи больше не определяет порядок реализации.

Реализация остаётся на Vue 3, Bootstrap 5, Pinia и текущем Django API. Макет задаёт визуальный ориентир; реальные маршруты, состояния и действия определяются приложением. Данные HTML вымышлены, кнопки открывают демонстрационные диалоги, поэтому его JavaScript нельзя переносить как прикладную логику.

## 1. Дизайн-спецификация

Извлечено из `.v2`, `.command-layout`, `.sidebar`, `command(role)`, `teacherRows()` и `studentRows()` в HTML.

| Назначение | Значение из макета | Применение |
|---|---|---|
| Фон | `#eef1f5` | Рабочая область |
| Поверхность | `#ffffff` | Таблицы, формы, шапка |
| Основной текст | `#1f2d3d` | Заголовки и данные |
| Вторичный текст | `#5c6878` | Подписи и пояснения |
| Акцент | `#315dcc` | Главное действие, активная вкладка |
| Граница | `#dbe1e9` | Разделители и контуры |

| Активный пункт | `#30445e` | Текущее местоположение |
| Радиус | `7px` | Основные поверхности; кнопки 6–8 px |
| Поле контента | `24px` | Desktop; на телефоне 16 px |
| Боковая панель | `175px`, в макете также `155px` | Начальная точка; увеличить при необходимости для RU/EN, не обрезать подписи |

Типографика: макет использует Segoe UI/Arial/sans-serif. Для реализации принять системный стек с кириллицей, заголовок страницы 25–28 px, заголовок блока 16–18 px, основной текст и строки 14 px, вторичный 12–13 px. Это осознанное увеличение мелкого текста 10–12 px из презентации. Для чисел включить `font-variant-numeric: tabular-nums`.

Убрать градиенты фона, стеклянные поверхности и декоративные крупные тени с переносимых экранов. Статусы сохранить с текстом: назначено, доступно, в процессе, зачёт, не зачтено, пропущено, не готов. Конкретные цвета статусов и их сочетания проверить на контраст перед фиксацией. Зелёный и красный не заменяют текст.

Компоненты: оболочка, боковая навигация, хлебные крошки, заголовок страницы, вкладки, компактная метрика, панель поиска, таблица, статус, состояния загрузки/ошибки/пустоты. Стек: существующие Vue-компоненты и CSS; Tailwind, React и shadcn не добавлять ради сходства с референсом.

## 2. Навигация и маршруты

Преподаватель: «Группы» и «Материалы» в постоянной навигации. Внутри выбранной группы — «Сводка», «Расписание», «Результаты», «Состав», «Настройки». Глобальный пункт «Результаты» из макета на первом этапе открывает выбор группы, а не выдуманную общую статистику. Без выбранной группы нельзя показывать показатели последней случайно открытой группы.

Студент: «Мои тесты», «Расписание», «Результаты». Эти представления используют существующий `/student` и параметр `view=assignments|schedule|results`, который предстоит реализовать. Существующие прямые ссылки без параметра открывают назначения. Поиск и фильтры хранить в URL, чтобы работали Back/Forward и обновление страницы.

Существующие `group-overview`, `group-details`, `subject-detail`, `topic-detail`, `attempt-detail` сохранить. Уже реализованный `?tab=results` у обзора группы должен продолжить работать. Состав и настройки остаются в GroupDetails; ссылки вкладок переходят туда. До добавления новых query-параметров проверить текущие значения в каждом экране, неизвестные значения заменять безопасным режимом по умолчанию.

Вход и 404 получают общую типографику и цвета, но вход не показывает рабочую боковую панель. Профиль, язык RU/EN и выход доступны в оболочке. Демо-переключатель ролей в приложение не переносить. Активная попытка использует ту же визуальную систему, с сохранением места под вопрос, навигацию и статус сохранения.

## 4. Данные и ограничения

- Студент уже использует `Student.getAllAssignments()` и `Student.getScheduledAssignments()`. Отдельный endpoint для переоформления списка не нужен, если проверка формы ответа подтверждает необходимые поля.
- Группа уже использует `Group.get()`, `getRanking()`, `getTeacherAssignment()`, `getTopicCalendar()` и операции сохранения расписания. Проверить на синтетических данных, есть ли количество отвеченных вопросов и все статусы из макета. Если поля нет, показывать честный доступный статус; не подменять его фиктивным прогрессом.
- В сводке преподавателя явно подписывать выбранные дату и назначение. Итог для одного назначения нельзя выдавать за результат по всей дисциплине.
- Считать метрики из полного набора данных выбранной области. При серверной пагинации не выдавать размер текущей страницы за общий счётчик. Если полного числа нет — скрыть агрегат или согласовать отдельное поле API.
- Одна попытка относится к конкретному назначению. Доступность и дата определяются сервером; начало будущего теста и произвольный повтор не появляются в результате редизайна.
- «В процессе» и «Не начато» в доступную дату не считать пропуском. Зачёт определяется порогом конкретного теста, не универсальным процентом.
- Общее межгрупповое аналитическое API, новые награды/XP, модель освоения тем и офлайн-прохождение — отдельные задачи, не условия этого редизайна.

## 5. Адаптивность и состояния

Desktop: sidebar + контент; три метрики; таблица с названием, датой/результатом, статусом и действием. Заголовок и основное действие остаются рядом с рабочим контекстом.

До 850 px: боковая панель становится компактной верхней навигацией, как в референсе. На телефоне пункты переносятся, текст не прячется за неоднозначными иконками. До 560 px: строки назначений/студентов превращаются в вертикальные группы с явными подписями полей. Сложную матрицу результатов допустимо оставить в отдельной подписанной области горизонтальной прокрутки. Горизонтального скролла всей страницы быть не должно.

Ширины проверки: 320, 390, 768, 1024, 1440 px; масштаб 200%; длинные имена и названия; RU/EN. На мобильном цель для основных интерактивных элементов — 44 px. Компактность обеспечивать отступами и структурой, а не текстом 10 px.

На каждом экране проверить: первоначальная загрузка, пустые данные, пустой поиск, ошибка с повтором, ошибка действия при сохранённом списке, запрет доступа, длинные данные. При загрузке и ошибке оставлять оболочку и контекст видимыми: демо скрывает всю screen-content, в приложении так делать не нужно.

Примеры текстов: «Назначений пока нет»; «По вашему запросу ничего не найдено» + «Сбросить поиск»; «Не удалось загрузить результаты» + «Повторить»; «Тест откроется {дата}». В попытке различать «Сохраняем…», «Сохранено на сервере», «Ответы сохранены на этом устройстве», «Не удалось отправить». Нельзя показывать подтверждение сервера до успешного ответа.

## 7. Приёмка

- Вход обеих ролей, переключение языка, выход, прямые ссылки, Back/Forward и обновление страницы работают.
- Преподаватель находит группу, назначает готовый тест, смотрит результат, изменяет состав и импортирует вопросы. Скрытые в новом меню функции не считаются сохранёнными.
- Студент находит назначение, продолжает попытку, завершает её и открывает разбор; будущие назначения доступны только согласно серверным правилам.
- Ошибка загрузки не выглядит как отсутствие данных; ошибка сохранения не подтверждает успех.
- Таблицы читаются с клавиатуры и экранным диктором; фокус видим; диалог возвращает фокус; активная навигация обозначена семантически.
- Проверены размеры выше, увеличение текста, контраст, reduced motion и длинные подписи. Мобильные строки сохраняют дату, статус и действие.
- Нет декоративных данных из HTML, новых лишних сетевых запросов на каждую строку, ошибок JS и потери текущей логики безопасности rich text.
- PWA после обновления получает согласованные HTML/CSS/JS; не остаётся оболочка старой версии с новыми экранами. Поведение кэша проверить по текущему service worker.

Проверки при реализации: `npm --prefix student-platform-frontend run build`; регрессии `npm --prefix student-platform-frontend run test:security` с предварительной сборкой и доступным браузером; `uv run python manage.py test accounts learning --noinput`. Добавлять сценарные браузерные проверки навигации и критических действий там, где меняется поведение; не писать тесты, утверждающие каждый CSS-отступ. До изменения API backend-тесты достаточно выполнить на финальной проверке совместимости. Для этого документа сборка и тесты приложения не запускались.

## Следующая конкретная работа

Начать с этапа 0, затем реализовать общую оболочку и два контрольных экрана: `GroupOverview` и `StudentHomePage`. Они проверяют основную идею «Рабочей станции» сразу для обеих ролей. После визуальной и функциональной проверки распространить систему на остальные экраны по указанному порядку.
